Quickstart

git clone https://github.com/reelmesh/GodotCoder.git
cd GodotCoder
npm install
npm run build
node dist/cli.js --help

Requirements: Node.js ≥22.19, Godot 4.3+ (native or Flatpak), Linux.

Run tests:

npm run test:smoke          # Build + 71 tests
tsx --test test/schema.test.ts         # Schema validators only
tsx --test test/godot-config-parser.test.ts  # Config parser
tsx --test test/repair-migrations.test.ts    # Godot 3→4 migrations

Your First Game — 60 Seconds

mkdir ~/my-first-game && cd ~/my-first-game
node ~/GodotCoder/dist/cli.js

Inside the interactive shell:

> /make make a 2d asteroid shooter where you dodge rocks

GodotCoder scaffolds a project, writes planning artifacts, builds the game, validates with Godot, and records the run. Launch it:

> /play

Or skip the shell entirely:

node ~/GodotCoder/dist/cli.js pipeline "make a 2d platformer with coins" --play

Workflow Recipes

Recipe: New Game from Scratch

Step 1 — Create project directory 
mkdir ~/my-game && cd ~/my-game
Step 2 — Plan the game 
node ~/GodotCoder/dist/cli.js plan "make a bullet heaven survivor game"

Writes .godotcoder/brief.md, gdd.md, technical-plan.md, tasks.md, and tasks.json.

Step 3 — Build first playable slice 
node ~/GodotCoder/dist/cli.js pipeline "make a bullet heaven survivor game" --play

Builds project, validates, launches in Godot.

Step 4 — Iterate with previews 
node ~/GodotCoder/dist/cli.js build "add enemy spawning waves" --preview
# Review diff, then:
node ~/GodotCoder/dist/cli.js build "add enemy spawning waves" --apply
node ~/GodotCoder/dist/cli.js validate
node ~/GodotCoder/dist/cli.js play

Recipe: Work with an Existing Godot Project

Step 1 — Inspect 
cd ~/my-existing-project
node ~/GodotCoder/dist/cli.js inspect --json
node ~/GodotCoder/dist/cli.js runtime doctor
Step 2 — Validate 
node ~/GodotCoder/dist/cli.js validate
node ~/GodotCoder/dist/cli.js validate --smoke   # Quick 3s test
node ~/GodotCoder/dist/cli.js validate --export  # Test export presets
Step 3 — Build a feature 
node ~/GodotCoder/dist/cli.js build "add a dash move with cooldown UI" --preview
node ~/GodotCoder/dist/cli.js build "add a dash move with cooldown UI" --apply
node ~/GodotCoder/dist/cli.js validate

Recipe: LLM-Powered Code Generation

Step 1 — Configure a provider 
# Local Ollama (free)
node dist/cli.js models use --provider ollama --model llama3.1

# LM Studio local server (free)
node dist/cli.js models use --provider lmstudio --model qwen/qwen3.6-27b

# OpenAI cloud
node dist/cli.js models use --provider openai --model gpt-4o --api-key-env OPENAI_API_KEY

# Anthropic cloud
node dist/cli.js models use --provider anthropic --model claude-sonnet-4-20250514
node dist/cli.js auth login --provider anthropic --api-key sk-ant-...

# OpenRouter cloud router
node dist/cli.js models use --provider openrouter --model openai/gpt-4o-mini
node dist/cli.js auth login --provider openrouter --api-key sk-or-...
Step 2 — Ask questions 
node dist/cli.js ask "How do I implement double-jumping in Godot 4 CharacterBody2D?"
Step 3 — Generate code 
node dist/cli.js build "add a dash move with cooldown UI" --llm --preview
node dist/cli.js build "add a dash move with cooldown UI" --llm --apply
Step 4 — Full LLM pipeline 
node dist/cli.js pipeline "make a cozy puzzle game about matching colors" --llm --play

Recipe: Fixing Validation Errors

Step 1 — Run repair 
node dist/cli.js repair --json
Step 2 — Inspect what changed 
node dist/cli.js repair list
node dist/cli.js repair diff           # Show latest diff
node dist/cli.js repair diff repair_20260616T120000_000000
Step 3 — Undo if needed 
node dist/cli.js repair undo repair_20260616T120000_000000

Recipe: Automated Playtesting

node dist/cli.js playtest --json
node dist/cli.js play --test

Runs the game headlessly for 5 seconds with input simulation, logs, artifacts, and simple interactivity heuristics. Returns structured errors and warnings:

{
  "ok": false,
  "errors": [
    "SCRIPT ERROR: Parse Error at res://scripts/player.gd:12"
  ],
  "warnings": [
    "No simple scene-state or text changes were observed during the playtest."
  ],
  "durationMs": 1234,
  "timeline": [
    { "atMs": 500, "kind": "input", "action": "ui_accept", "pressed": true }
  ],
  "interactivity": {
    "appearsInteractive": false
  }
}

Records are stored under .godotcoder/playtests/, including latest.json for future build context.

Build System

The build system uses the configured LLM to generate all game code:

TriggerSourceOutput
Default (always)Configured modelOpen-ended game code, any genre

Preview mode (default) shows a line-level diff before writing:

Build preview
Adds a health bar HUD to the main scene
create res://scripts/hud.gd (+24 -0, 0 → 24 lines)
--- /dev/null
+++ res://scripts/hud.gd
+extends Control
+var health := 100
+func _ready() -> void:
+    update_bar()
...
modify res://scripts/main.gd (+3 -0, 42 → 45 lines)
  func _ready() -> void:
      print("ready")
+     var hud = preload("res://scripts/hud.gd").instantiate()
+     add_child(hud)

Apply with /apply (shell) or --apply (CLI). Reject with /reject.

Applied builds record under .godotcoder/patches/<patch-id>/record.json with:

  • File operations (create/modify/unchanged)
  • SHA-256 hashes (before/after)
  • Linked validation report IDs

LLM Acceptance Gates

LLM-generated code must pass all gates before application:

  • SCENE Must produce or update a scene
  • SCRIPT Must include a gameplay GDScript
  • INPUT Must handle input or frame processing
  • FEEDBACK Must have visible player feedback
  • OBJECTIVE Must define a goal/fail/restart loop
  • GODOT 4.3+ Must use modern Godot 4 APIs only

Repair Engine

The repair loop: Validate → Detect errors → Apply deterministic fixes → Revalidate.

Repair Rules

CategoryRuleWhat it does
Missing filesBroken script referenceCreates placeholder .gd with extends Node
Missing filesBroken scene referenceCreates minimal .tscn with Node2D root
Missing filesBroken resource referenceCreates placeholder .tres or SVG image
Migrationexport var→ @export var
Migrationonready var→ @onready var
Migration.instance()→ .instantiate()
Migrationyield(owner, "signal")→ await owner.signal
MigrationKinematicBody2D→ CharacterBody2D
MigrationPoolByteArray etc.→ PackedByteArray etc.
MigrationOS.get_ticks_msec()→ Time.get_ticks_msec()
Migrationdeg2rad()→ deg_to_rad()
Migrationrand_range()→ randf_range()
Migrationconnect("s", t, "m")→ s.connect(t.method)
Migrationtool→ @tool

More: export(float, ...) → @export_range, export(FILE, ...) → @export_file, linear2db → linear_to_db, db2linear → db_to_linear, KinematicBody3D → CharacterBody3D, Navigation2D → NavigationRegion2D.

Model adapter details

  • OpenAI-compatible: POST /chat/completions
  • Anthropic: POST /messages, system prompt as top-level field
  • Ollama: POST /api/chat
  • LM Studio: POST /api/v1/chat, typed input blocks, extracts from output arrays (skips reasoning items)
  • OpenRouter: GET /api/v1/models and POST /api/v1/chat/completions, Bearer auth plus X-OpenRouter-Title and optional attribution overrides

Godot Editor Plugin

Location: addons/godotcoder/. Enable in Project Settings → Plugins.

Configure the CLI Path in the dock to point to your godotcoder binary. The plugin communicates with the CLI through subprocess JSON — it does not own model orchestration, memory, or providers.

Editor Context JSON

{
  "current_path": "res://scenes/main.tscn",
  "scene_root": { "name": "Main", "class": "Node2D", "path": "res://scenes/main.tscn" },
  "selected_nodes": [

  ],
  "current_script": { "class": "GDScript", "path": "res://scripts/player.gd" }
}

Auto-attach: When editor context is captured, all subsequent RPC calls include it automatically. History persists in user://godotcoder/plugin-history.json.

History controls: Replay Last (⌘R), Replay Selected (select from list), Clear history. Each entry stores the full command payload for exact replay.

Plugin Test Plan

  1. Enable addons/godotcoder/ in a Godot project
  2. Open a scene with at least one selected node and one open script
  3. Click Capture — confirm dock shows structured editor context JSON
  4. Run Status, Inspect, Validate — confirm responses include editorContext
  5. Click Explain — confirm summary of selected scene/node/script + project counts
  6. Click Review — confirm git status is reported (read-only)
  7. Click Scene — confirm scene existence check against project index
  8. Paste a Godot error, click Debug — confirm subsystem, source file, next steps
  9. Enter a build prompt, click Preview — confirm file counts + changed paths (no writes)
  10. Click Reject — confirm pending preview state clears without writes
  11. Preview again, click Apply — confirm the dock calls CLI-owned apply orchestration
  12. Click Summaries — confirm latest validation, visual, and repair summaries render
  13. Use Replay Selected on an older entry — confirm exact command is replayed
  14. Change CLI path to invalid value — confirm dock shows clear failure message
  15. Change selection, capture again — confirm history grows and context updates

Design Principles

  • CLI-first: Fast terminal start, no editor required
  • Linux-first: Native + Flatpak Godot as first-class targets
  • Godot-native: GDScript, scenes, resources — no non-Godot runtimes
  • Godot as judge: Validation through the actual Godot executable
  • Small steps: Preview → review → apply → validate
  • Recoverability: SHA-256 patches, repair records, undo support
  • Knowledge priority: Local files → Official docs → Skills → Datasets → Model knowledge
